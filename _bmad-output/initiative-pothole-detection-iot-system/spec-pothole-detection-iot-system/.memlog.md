- (event) headless run; express distill; input = in-chat engineering brief (rich, pre-sorted); no active_initiative so spec written loose under output_folder; slug derived from brief title
- (direction) objective: vehicle-mounted system captures road video, IMU motion data and location, detects potholes, shows live results on two displays: 7in screen on Pi (Dashscreen) and presentation dashboard on laptop
- (capability) CAP-1 IMU: Pi reads IMU and exposes latest sample at GET /imu/latest; laptop polls it; live IMU shown on Dashscreen and Dashboard
- (capability) CAP-2 Video: Pi serves USB webcam feed as HTTP stream from motion; laptop pulls it for playback and detection
- (capability) CAP-3 GPS source: laptop serves latest location at GET /gps/current (fake replayed route first, real source later); Pi can curl it and get valid JSON
- (capability) CAP-4 Dashscreen: Pi polls laptop for GPS and shows map (pin + trail) and IMU data on 7in LCD; pin moves on screen
- (capability) CAP-5 Stale fix: Pi Dashscreen shows an explicit stale state when GPS ts is too old, instead of a wrong position
- (capability) CAP-6 Detection: laptop runs pothole detection on the pulled video, outputs severity and confidence per detection, annotated video plays on laptop
- (capability) CAP-7 Dashboard: laptop shows map, IMU, annotated video and HUD (speed, heading); window can move to an external screen for presentations
- (capability) CAP-8 Standalone demo: each device side runs and demos against simulated counterpart (fake_gps route replay, fake_imu samples) without the other device
- (constraint) transport is HTTP polling only; no websockets or push (fixed)
- (constraint) IMU reaches Pi over UART (fixed per brief) - see open question on UART vs I2C
- (constraint) video is HTTP stream from motion on Pi (fixed); detection runs on laptop, not Pi
- (constraint) location source is the laptop; Pi polls it; Pi's own GPS module is dead and unused
- (constraint) every payload timestamped at its source (ISO 8601 UTC); Pi and laptop clocks synced with NTP, else detections misalign with IMU/GPS
- (constraint) video and telemetry share one Pi-laptop link; full run must work on a dedicated network (Ethernet or dedicated hotspot), WiFi contention risks lag/drops
- (constraint) code organised by deployment target (rpi/, main_server/); payload definitions and config come from one shared module imported by both devices
- (decision) non-goals: websockets/push transport; using the dead GPS module; cloud sync or persistent storage; multi-vehicle support
- (decision) success signal: full end-to-end run on dedicated network - Dashscreen pin+trail moves with live IMU, laptop Dashboard on external screen shows map, live IMU, annotated video with severity/confidence, HUD; pins match real positions
- (note) GPS payload: lat,lon float required; ts ISO8601 UTC required (source-stamped); speed_kmh,heading float optional (fills HUD); accuracy_m float optional (lets UI flag weak fix)
- (note) interfaces: IMU sensor->Pi UART; video Pi->laptop HTTP stream from motion; GPS laptop->Pi Pi polls GET /gps/current; IMU for dashboard Pi->laptop laptop polls GET /imu/latest (same pattern as GPS)
- (note) poll intervals recommended: GPS 1s, IMU 100ms; map needs no faster
- (note) components Pi: IMU reader (UART, expose latest sample); webcam stream (motion, serve USB webcam to laptop); GPS client (poll laptop for fix); Dashscreen (map pin+trail and IMU on 7in LCD)
- (note) components laptop: GPS service (latest location over HTTP); image processing (detect on video, severity+confidence); Pi client (pull IMU and video from Pi); Dashboard (map, IMU, annotated video, HUD; movable to external screen)
